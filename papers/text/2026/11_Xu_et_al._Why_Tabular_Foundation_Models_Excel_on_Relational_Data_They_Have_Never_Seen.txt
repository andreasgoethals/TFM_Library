ABSTRACT
Given a relational database (RDB) storing heterogeneous tabular information, how
can we predict missing (or future) values in some target column of interest? As
candidate targets are numerous in enterprise settings, it is preferable to avoid
learning a new model from scratch each time there is a new prediction task. Frozen
foundation models (FMs) based on in-context learning (ICL) and RDB-specific
pre-training provide a viable solution, but the ideal design still remains largely
unresolved. Perhaps unexpectedly, preliminary evidence has recently shown that
existingsingle-table FMs(aka TFMs), when combined with suitable parameter-free
relational encoders, can be quite competitive in practice despitezero exposure to
RDB pre-training or relational data of any kind. In this work we first empirically
confirm this phenomenon with a more diverse array of experiments. We then turn
to our main contribution, namely, surfacing multiple complementary explanations
for why TFMs behave so effectively. These explanations ultimately hinge on
innate synergies whereby parameter-free encoders map relational effects to fixed-
length embeddings that loosely mimic distributions for which TFMs were originally
designed; in so doing, desirable single-table properties transfer to relational settings
(e.g., convergent posterior predictive distributions). Collectively, our analysis
forges new pathways for improving RDB FMs, particularly when we prioritize
interpretability and inevitable integration within agentic systems.
1 INTRODUCTION
Relational databases (RDBs), housing collections of interrelated tables, are indispensable across enter-
prise applications and e-commerce platforms (Garcia-Molina et al., 2009). From a machine learning
standpoint, the information stored within just a single RDB often contains countless possibilities for
predictive modeling, covering targets such as customer retention, user churn, or click-through rates
(Dave et al., 2014; Motl & Schulte, 2015; Ni et al., 2019; Zykov et al., 2022). Of course retraining a
new model from scratch to address each new predictive task of interest may be prohibitively laborious
or expensive, which motivates a new class of foundation models (FMs) specifically tailored for RDBs.
Among others, these vary from LLM-based approaches that digest serialized RDB content (Wydmuch
et al., 2024), to specialized Transformers pre-trained based on in-context learning (ICL) (Fey et al.,
2025; Hudovernik et al., 2026; Ranjan et al., 2026c; Wang et al., 2026b), the common theme in each
case being afrozenarchitecture capable of making predictions involving arbitrary unseen RDBs.
As a robust and scalable alternative, it has recently been demonstrated thatsingle-table FMs(aka
TFMs), when combined with suitable parameter-free subgraph encoders for capturing multi-table
relational context, can perform well without requiring any RDB-specific pre-training (Grinsztajn
et al., 2026; Hayler et al., 2026; Xu et al., 2026). After presenting background RDB context in Section
2, our work herein centers around confirming and explaining this unexpected performance via:
• Comprehensive demonstration.We provide thorough empirical comparison of wide-varying
RDB foundation models across diverse benchmarking tasks. These results from Section 3 solidify
the surprising effectiveness of TFMs repurposed for relational data.
• Explanatory theory.In Sections 4–7, we elucidate multiple complementary factors that help
explain this phenomenon and broader merits of TFMs. Specifically, we show that TFM-based
approaches: (i) naturally handle varying degrees of relational context, forming a continuum from

2 BASICS OFRDB FOUNDATIONMODELS
The goal of an RDB foundation model is to retain applicability across unseen RDBs, ideally with no
retraining for each new predictive task. Beyond direct LLM-prompting approaches (Wydmuch et al.,
2024), we now discuss recent pipelines designed to natively handle RDB/tabular data.
2.1 PREDICTIVEMODELING WITHRELATIONALCONTEXT
Suppose we have training data {xi, yi}n i=1 ={X,y} composed of instance feature rows xi ∈ Xd
along with associated instance labels yi ∈ Yfor all i. The objective is to learn a parameterized
model fθ that achieves fθ(xtest)≈y test at any test point {xtest, ytest}, where in practice ytest is unknown.
RDB predictive modeling generalizes this canonical ML scenario by integrating an additional set of
auxiliary data tables T={T k}K k=1, where T k ∈T nk×dk denotes the k-th table associated with a
given entity type. Each table row corresponds with a single instance of that entity (e.g., a purchased
item), while columns reflect heterogeneous instance attributes (e.g., product information). Note that
w.l.o.g., we also assume T 1 =X . Lastly, an RDB also includes a set of relations R expressed as
primary key (PK), foreign key (FK) pairs (Garcia-Molina et al., 2009); these may be absorbed into
the constituent tables of T as additional columns when convenient. Both supervised methods and
FMs leverage these auxiliary tables for making predictions.
2.2 COMPUTINGRDB EMBEDDINGS
To make use of relational context for predictive tasks, the basic strategy is to first convert a given
labeled RDB D:={T,R,y} to a heterogeneous graph G. This typically involves treating each table
T k as a node type and each row i within a given T k as a node with features tk i (Cvitkovic, 2020;
Dwivedi et al., 2025; Fey et al., 2023; Zhang et al., 2023a;b). Directed edges can then be formed
using each PK-FK pair within R. We next sample H-hop subgraphs or ego-networks GH (xi) from
G that are centered at each target row xi within X. Importantly, sampling fortemporalRDBs should
exclude nodes with time-stamps later than xi. These subgraphs form the input to an RDB encoder
gϕ, instantiated as some form of graph neural network or Transformer architecture with (optional)
parametersϕ. This facilitates computation offixed-lengthembeddingsz i =g ϕ[GH (xi)]∈R dz.

Retrofitting TFMs with a relational encoder.Given the growing range of single-table FMs
(Hollmann et al., 2025; Jingang et al., 2025; Qu et al., 2026; Zhang et al., 2025b;a), it is natural to
consider combining with aparameter-freeencoder gpf, for flattening RDB neighborhoods into fixed-
length tabular features, such that the entire pipeline requires no RDB-specific training/pre-training
(Grinsztajn et al., 2026; Hayler et al., 2026; Xu et al., 2026) (a conversion akin to U k ←T k, as
adopted by the pre-trained ICL-based model from Hudovernik et al. (2026) described above, may
be optionally considered as an additional pre-processing step, but we do not pursue this possibility
further). Herein we aim to confirm and explain the effectiveness of these simple approaches relative
to more complex alternatives.

Results.We compare across a suite of six diverse benchmarks from Appendix E, each composed
of multiple RDB predictive tasks. We remark that it is routine to only report results on RelBench-

Why are TFMs so competitive on RDBs?It is initially reasonable to assume that pre-training
RDB-specific FMs using actual RDB data (real or synthetic) is essential for achieving strong inference-
time performance on unseen relational data. So how can TFMs paired with some gpf possibly perform
well, as we have confirmed in Figure 1. The high-level argument from Xu et al. (2026) is that prior to
3

seeing ICL samples, a data-agnostic encoder is incapable of adjudicating column roles, which may
vary from dataset to dataset (or even task to task within a given RDB). This phenomenon advantages
RDB encoders that only compress verticallywithinhigh-dimensional columns (where shared units
facilitate interpretable aggregation), not horizontallyacrosscolumns, where relevance is largely
indeterminate without adequate label information. Conditioned on this restriction to vertical (intra-
column) compression, Xu et al. (2026) detail how gpf can result in minimal loss of expressiveness,
while naturally pairing with existing TFMs to form a complete RDB pipeline. While promising as an
analytical starting point, there remains considerable ambiguity regarding the rationale and surprising
empirical efficacy of this simple recipe. In the remainder of this work we take several disambiguating
steps, beginning with a discussion of the blurry line between single tables and RDBs, where TFMs
already work well on the former.
4 SINGLETABLES ANDRDBS ON ACONTINUUM
Inducing RDBs from single tables.Conventionally, TFMs and benchmarking (i.e., single-table
regimes) are treated separately from their RDB counterparts. But as we now examine, infinitesimal
adjustments to an initial single-table setup facilitate gradual transitioning to multi-table relational
scenarios, making any strict partitioning somewhat arbitrary. Concretely, beginning with a single-
table scenario, meaning K= 1 and features T 1 =X , we can trivially transform these data into two
or more tables with arbitrarily-small, labeled cross-row relational dependencies as follows:
1. Select any categorical column of T 1; w.l.o.g. assume B categories. If no categorical columns
exist, then we simply chose a numerical column and quantize intoBbins.
2. Form a new auxiliary table T 2 with a single length-B column, where elements are the unique
categories obtained from step 1 above. Treat the lone column withinT 2 as a PK, and the original
categorical column withinT 1 as an FK.
3. To induce more complex schema, we may optionally repeat steps 1–2 using otherT 1 columns.
4. Form subgraphs GH (x) seeded at any row x; provided H≥2 , these neighborhoods will include
multiple nodes associated with different rows of X. This is because the first hop reaches an
induced T k (k >1), while any second hop returns to T 1. In doing so, cross-row relational
dependencies are introduced via the edges withinG H (x)(Gan et al., 2024).

candidates for navigating relational continuums, providing a strong initial plausibility argument for
their usage on RDBs. Conversely, if an alternative RDB FM does not work well on single-tables,

Overall, RDBLearn shows the best performance among RDB FMs, demonstrating the ability to
mostly discard distracting relational effects that are not necessary for making predictions. Meanwhile,
although RT-J struggles with some of these tasks, KumoRFM-2 performs significantly better (exclud-

represents an informative hurdle for RDB FMs to pass. It is also worth noting that on three regression
tasks, RDB FMs actually surpass the performance of the non-relational baseline, and the RDBLearn
average regression performance modestly exceeds TabPFN-v3 (see Appendix F).

5.2 NATURALALIGNMENT WITHSINGLE-TABLEFMS.
Uniform ICL sampling.When choosing ICL samples, we would like at least some associated
with encoder representations {zi}n i=1 that are reasonablycloseto the test point representation ztest, as
required for unbiased estimation per Proposition 5.2. In the absence of domain-specific knowledge
or strong a priori assumptions such as homophily,1 we may not know in advance where these close
samples will be located in a given RDB. And yet FM architectures should ideally address wide-
ranging conditions with a shared data-agnostic strategy. Along these lines, uniform sampling (from
rows of X with historical timestamps) is reasonable for approximating the full RDB context across
generic new tasks, leading to at least some coverage of any newztest with select elements of {zi}n i=1.2
Moreover, in a sufficiently large RDB these uniform samples may even behave roughly as though
they were IID, mirroring the single-table distributions for which TFMs were originally pre-trained.
This alignment can play a critical role in achieving more robust performance as the number of ICL
samples grows, which we will investigate next through the lens ofposterior predictive distributions
(PPDs) (M¨uller et al., 2021). The PPD serves a critical role, representing the target distribution that
ICL-based TFMs attempt to approximate during pre-training (Hollmann et al., 2022).

is based. But it is nonetheless useful to contrast this notion with distinct options adopted by other
types of RDB FMs. For example, the latest SOTA relational Transformer instantiation RT-J (Ranjan
et al., 2026b;c), based on RDB-specific pre-training with real-world RDB data, involves forming ICL
samples as the set of target rows in T 1 that are most frequently visited over the course of a large
number of fixed-lengthrandom walksseeded from xtest. In this way we collect samples that are close
to xtest in the sense of graph distance,but not necessarily in terms of encoder representation. For
networks dominated by homophily effects, meaning nearby nodes in the graph have similar labels,
this likely works well. But more broadly, within an RDB influenced by heterophily relationships,
disconnected regions, or other spurious network effects, similar samples/nodes drawn from random
walks maynotbe similar in terms of encoder representations, in which case the necessary conditions
of Proposition 5.2 would not hold. This may also partially explain the performance of RT-J in Figure
2, where the infused relational structure is minimally related to the labels by experimental design.

influences the PPD upon which ICL-based FMs depend. For example, regardless of whether the
measure µ reflects a single-table or a full RDB pre-training prior, if random-walk sampling is
adopted to obtain Sn, then the core IID assumption from (5) used to establish (6) will no longer
generally hold. Consequently, increasing the number of ICL samples need not approximate a desirable
asymptotic regime, and the resulting PPD may bear little resemblance to the target pgt

Dilemma of RDB-specific pre-training priors.Now suppose that µ is no longer simply a prior

6 ADEQUATEENCODEREXPRESSIVITY EVEN WITHNO PARAMETERS
We next address possible expressivity limitations associated with gpf usage, the key ingredient which
allows TFMs to avoid any RDB-specific training or pre-training. A natural presumption here is that
parameter-free encoders place a potentially-burdensome restriction on the types of RDB neighborhood
representations available for constructing ICL samples. We analyze this concern through a case study
involving interaction terms, where we find that the added expressivity of parameterized encoders gϕ
need not provide an unequivocal advantage over the much simplerg pf adopted by TFMs.
Interaction terms as a case study.Prior work has noted that parameter-free encoders that process
RDB columns individually (as mentioned in Section 3 and adopted by RDBLearn/TabPFN-Rel)
are incapable of handling interaction terms between columns in auxiliary tables. Along these lines,
consider the following representative example of this ostensible limitation discussed by Hudovernik
et al. (2026); Huang et al. (2026). Suppose we are given an RDB with only two tables: A labeled
target tableT 1 =yand a child tableT 2 = [a,b]composed of two binary feature columnsaandb.
A PK associated with each row of T 1 is linked by FKs to one or more rows of T 2, where Ri denotes
the set of rows within T 2 that have FKs pointing to the PK associated with row i in T 1. Ground-truth
labels are then constructed to satisfy
yi = max j∈Ri [aj ∧b j]∀i.(7)
Clearly the element-wise interactions aj ∧b j determine the label, and so the argument goes, excluding
such interactions is disproportionately problematic within any gpf that encodes columns separately as
advocated by Xu et al. (2026). We provide three counter-points to this concern:
Alllossy encoding involves negative counter-examples.The labels computed via (7) involve a
binary function over a 2|Ri|-dimensional input space, giving 22|Ri| = 4|Ri| possible input config-
urations.But this is just one possible function sharing this input range. Assuming no permutation
invariance across rows, there are 2(4|Ri |) distinct binary functions expressible over the same input
space. Without external knowledge mandating which function is correct, an encoder that fails to
losslessly preserve the entire input range will make it impossible to guarantee that a subsequent
decoder can determine the correct labeling rule; a single missing bit can flip any labeling rule leading
to errors within an arbitrary downstream classifier.
More broadly, all lossy encoding,whether parameterized or not, opens up a set of inevitable counter-
examples, whereby learning the correct function is infeasible; see Xu et al. (2026)[Proposition 4.2] as
one representative scenario. This remains true even if task-specific labels are included within GH (x);
more on this in Appendix B. Consequently, the primary differentiating consideration is not whether
counter-examples exist; rather, what matters is the relative frequency with which encoder-specific
counter-examples appear in real-world RDBs. 3 In general, functional expressivity is likely more
critical insupervisedscenarios, where trainable degrees-of-freedom can be mapped to task-specific
encoders that mitigate task-specific counter-examples (e.g., a particular set of interaction terms). But
for ICL-based FMs restricted to a fixed data-agnostic form, other factors such as interpretability or
sample complexity may matter more than parameterized expressivity per se.
3This is admittedly difficult to quantify, as we usually only have reported results on final predictive accuracy.
8

Arbitrary interactions challengeanyfixed encoder.Even if we restrict label generation to
functions of interaction terms similar to (7), parameterized encoders still do not have a clear-cut
advantage in real-world settings. This is because real-world auxiliary tables often have many
columns. Excluding all higher-order interactions, there will still exist a quadratically expanding
number of candidate interaction terms as the number of columns grow. Without knowing in advance
which are important, lossy encoder compression,parameterized or not, will create the potential for
prediction errors (i.e., there will always be cases where needed interaction signal depends on missing
information). Appendix B analyzes how historical labels within GH (x) cannot generally resolve this
ambiguity under certain settings.
Parameter-free encoders can (sometimes) handle interactions.For arguments sake, the pre-
sumption thus far in this section has been that a column-wise parameter-free gpf cannot represent
interaction terms. But actually, this is not strictly true for the following two reasons. First, models
like RDBLearn or TabPFN-Rel can directly handle interactions between compressed representations
of individual columns; these representations form additional columns within Z∈R n×dz, and TFMs
can readily handle interactions between the constituent ICL features. Secondly, with enough aggrega-
tions of a suitable type, lossless compression is possible to enable interactions, at least in principle.
For continuous aggregators (Corso et al., 2020), the required cardinality is equal to the number of
real-valued elements being aggregated (not surprising), noting that these aggregators need not be
permutation invariant (e.g., they could be time-dependent, involve symmetry-breaking projections,
etc., for resolving ordered column values). But if arbitrary discontinuities are allowed (which is
admittedly not practically feasible to implement), even just a single aggregation is technically capable
of reconstructing the full set (Rubio-Madrigal & Burkholz, 2026); this conclusion follows from the
Kolmogorov-Arnold representation theorem (Schmidt-Hieber, 2021).
Interaction experiments.We conduct multiple tests to explore the impact of interaction terms;
see Appendix G for full details. For the first, we generalize the setup of (7) to include 4 different
interaction types involving columns {a,b} in T 2; we then compare TFM-based RDBLearn against
the top non-TFM-based RDB FMs, KumoRFM-2 and RT-J. Figure 3 (left) shows the prediction
results as the width of T 2 is increased by adding uninformative columns. These distracting columns
follow the same distribution asa and b, and models do not know in advance which columns are useful,
raising estimation difficulty. Overall, we observe that RT-J does not work well in these settings, likely
because the implicit graph is disconnected, which can disrupt the collection of suitable ICL samples
(see Section 5.3). Meanwhile, RDBLearn is consistently competitive with KumoRFM-2, and actually
displays more stable performance across table width. This occurs because the aggregated features
from gpf can be combined by the subsequent TFM, at times forming usable approximations despite
not explicitly computing most interaction terms (see further details in Appendix G). Although we do
not pursue further here, expanding the aggregation set within gpf can in principle reduce RDBLearn
prediction errors beyond what is shown.
For the second test, we begin with the rel-trial dataset (Robinson et al., 2024) and compute new
ground-truth labels via interactions between sets of auxiliary table columns. Results are shown in
Figure 3 (right) across 9 different column interaction pairs (x-axis) used for generating labels. While
these tasks are challenging for all methods, RDBLearn generally outperforms the others (agentic
results included on this bar plot are addressed in Section 7).

Feature discrimination in three stages.RDB predictive modeling depends heavily on the ability
to differentiate, on a task-specific basis, informative versus non-informative features, relational or
otherwise. There are (at least) three candidate stages where such feature screening may plausibly take
place: symbolically prior to any FM application, viareasoning agentswith access to task-dependent
meta-data or domain expertise (stage 1); locally at the RDB encoder level using whatever context is
available within GH (x) (stage 2); and globally at the decoder level in a purely data-driven manner,
using the full range of labeled ICL samples (stage 3). It is our assertion that TFM-based models
are particularly adept at utilizing all three stages ascomplements, particularly because their gpf can
reduce potential interference between stages. In support of this conjecture, we offer the following:
Stage 2 as a conduit from the symbolic to the data-driven.Given the previously stated capabilities
of stages 1 and 3, a plausible role for stage 2 becomes relatively transparent: Make sure any features

Among other things, this entails that if a particular set of features are designated as possibly useful
by stage 1, they are not mixed together; some may be valuable, others ultimately not, but that
is for stage 3 to decide in a data-driven manner (per results from Xu et al. (2026), this task is

2 without alteration or attenuation. For example, this feature could be a specific interaction term

1. Or alternatively, various aggregations over temporal windows might be incorporated to reflect
known recency biases. Of course numerous other pragmatic possibilities exist as well, which can be
iteratively explored by an agentic system, with robust and scalable validation facilitated by TFMs.
TFMs innately honor stage 1–3 roles.When we adopt TFMs, equipped with an appropriate gpf,
any designated golden feature from stage 1 can simply be appended to others in stage 2 without
deviating from the original tabular setting under which stage 3 pre-training was conducted. But
this need not be the case for existing RDB FMs with parameterized gϕ. For the latter, there is
no guarantee that any input dimension/feature, golden or not, will be preserved within the output
embedding. Moreover, if we simply append such features to the encoder output (bypassing the
parameterized encoder itself), we then introduce potential mismatch from the original RDB-specific
pre-training regime of these architectures. There is also the larger related issue ofinterpretability. An
agent can directly reason over the SQL-based aggregations used to form gpf and offer suggestions
regarding what useful factors might be missing. In contrast gϕ is much more opaque since the output
embeddings result from stacked Transformer layers, e.g., there is no obvious way for an agent to tell
if a valuable interaction term is attenuated or absent altogether.
Empirical corroboration.Consider the hypothetical scenario whereby an agent (stage 1) with
domain knowledge materializes a golden feature; namely, an interaction term which determines the
downstream label is added as a new column (see Appendix G). Figure 3 (right) results show that
RDBLearn leverages this information to consistency boost performance in line with the three-stage
perspective from above. RT-J and KumoRFM-2 experience more modest gains, and in certain cases
do not capitalize at all on the provided golden feature (e.g., p-val ×onesided, p-val×disp-sd cases
from the figure), suggesting that the respective pipelines have somehow attenuated or underutilized
this golden feature. We further explore real-world implications in Appendix H, whereby RDBLearn
with a single coding-agent prompt can match the performance of a SOTA multi-agent system (Huang
et al., 2026) that trains numerous modelssupervisedon a per-task basis. Moving forward, we also
emphasize that adefaultexpectation should be that any agentic system built on top of tabular base
models will likely exceed the benchmark performance of pipelines such as RDBLearn and TabPFN-
Rel-OSS. This is because as public open-source projects, their design choices represent an observable
starting point with known performance upon which to calibrate any additional enhancements, albeit
at the cost of significant leakage concerns discussed in Appendix D.

Despite never seeing relational data (real or synthetic) during their pre-training stage, empirical

A.2 BENCHMARKINGIMPLICATIONS OF THECONTINUUMPERSPECTIVE
If there were always a clear-cut distinction between single tables and RDBs, then benchmarking
would be straightforward: simply partition into separate domains and evaluate accordingly, RDB
FMs tested only on RDBs (e.g., RelArena, RelBench, 4DBInfer, etc.) and TFMs only on single tables
(e.g., TabArena). But in light of the continuum described in Section 4, is such strict partitioning
unequivocally warranted?
For example, consider breaking out of this mold by applying an RDB FM to a suite of traditional
tabular benchmarks. If performance is competitive relative to frontier TFMs that specialize on single
tables, then our confidence in the robustness of this RDB FM justifiable grows. But now suppose
instead that performance is notably lagging. It is tempting to simply discount such cases as the
magisteria of single-table FMs and move on; however, the continuum perspective complicates any
such immediate dismissal. After all, if an RDB FM does not work well on single-tables, what about
performance on RDBs along a continuum that are minimally different from single tables? More
broadly, it is reasonable to question how large is the multi-table relational neighborhood around
any single-table benchmark within which unsatisfactory predictions are likely to be produced. Or
conversely, we may ask how large along any continuum must this neighborhood grow before the RDB
FM capabilities begin to outshine TFM alternatives by exploiting relational effects. It is precisely
these factors that (at least partially) motivate RDB FMs based on TFMs that already perform well on
single tables.

inform foundational questions of RDB FM development.

uninformative columns using the signal within a given U k alone). However, further treatment of
these possibilities lies beyond the scope of this work.
C ADDITIONALICL SAMPLINGCONSIDERATIONS
C.1 EVALUATINGSAMPLECOMPLEXITY
We remark that Ranjan et al. (2026b;c) emphasize the impressive sample efficiency of RT-J relative to
TFM-based RDBLearn, ostensibly requiring many fewer labeled ICL samples to achieve competitive
performance. But there are two key factors that merit consideration when interpreting the empirical
comparisons upon which this claim is based:
Different notions of sample complexity.ICL samples in Ranjan et al. (2026b;c) are only counted
per test instance, as opposed to counting thetotalnumber of unique samples required across an entire
test set, i.e., the union of unique samples extracted over all test instances associated with a given task.
This distinction is critical, since RDBLearn is designed to adopt afixedICL batch that is shared over
all test instances, while RT-J requires anewbatch for each separate inference point. Obviously then,
18

the cardinality of the fixed RDBLearn set will generally be larger than what RT-J adopts for just a
single test instance. But if we compute the average number ofuniqueICL samples needed per test
instance, RDBLearn may operate using far fewer depending on the RDB task. Hence RDBLearn can
potentially be more sample efficient relative to RT-J per this alternative metric as the number of test
points grows larger. This distinction impacts not only the required number of labeled observations,
but also execution costs, since RDBLearn need only extract ICL samples and construct a fixed TFM
KV cache once per task, regardless of how many test points exist.
Model alignment.The actual per-instance empirical ICL sample complexity results reported in
Ranjan et al. (2026b;c) are not directly based on an RDBLearn specification from either Xu et al.
(2026) or Xu & Wipf (2026). Instead, the RDBLearn pipeline is restricted to the TFM base model
TabICL-v2 and paired with much smaller per-instance ICL sample batches originally prepared for
RT-J (via random-walks combined with BFS local searches). Notably, RT-J pretraining is explicitly
aligned with this particular ICL-sampling regime, while RDBLearn is nominally designed for larger
fixed ICL sets (per motivations from Section 5). Even so, our central point here is not to discount
the prior comparisons between RT-J and RDBLearn from Ranjan et al. (2026b;c), which certainly
convey a useful complementary perspective, particularly if the goal is quantifying minimal sample
complexity costs for a single test point executing from scratch. Rather, we are simply advocating
that additional factors provide important balance, especially when weighing diverse tasks involving a
multiplicity of test points.
C.2 DEGENERACYEXAMPLE FROMRANDOMWALKSAMPLING
Assume data drawn according to Definition A.1, with original feature table T 1 =X and correspond-
ing labels y, as well as induced auxiliary table T 2 ∈ CB composed of a single PK column. The latter
is assumed to correspond with a categorical column in T 1 that we treat as an FK column pointing to
the PKs in T 2. Granting this simplified setup, we observe that any random walk originating at an
arbitrary row i of T 1 will at most reach |Ri| rows of T 1. Here Ri denotes the set of rows within T 1
that share the same FK value as row i. There is no mechanism for longer random walks to eventually
extend across the entire RDB; each must stall within Ri because ultimately the underlying graph G
extracted from the RDB is not fully connected.
The graph underlying the experiments shown in Figure 3 exhibits an analogous phenomenon. The
only difference is that the FK column switches from (implicitly)T 1 to (explicitly) T 2 in this example,
while the corresponding G remains disconnected. This might help explain why the RT-J model
does not happen to work as well within the particular context of the Figure 3 experiments (note that
RDBLearn would also not perform well here if forced to adopt the same RW sampling procedure).
That being said, if the RT-J context budget is not filled by random-walk accessible rows, a fallback
involving hybrid uniform sampling akin to RDBLearn could represent a potential workaround.
D LANGUAGEMODELAGENTUSAGE
A growing body of evidence suggests that LLM agents can play a useful role in tabular model
development (Han et al., 2024; Huang et al., 2026; Kim et al., 2026; Zhang et al., 2024). That being
said, their usage in the specific context of RDB predictive modeling involves notable caveats from
a benchmarking perspective. One in particular relates to potential leakage issues that may obscure
the degree to which we can plausibly extrapolate benchmarking results to expected performance
within new siloed industry settings. This concern stems from the fact that existing public benchmarks
are scarce, largely because of privacy concerns with real-world data. And yet predictive solutions
addressing the few RDB datasets that do exist, often involving feature engineering and human
expertise, are readily visible to frontier LLM agents during their pre-training process or during
inference-time retrieval. Hence agent-based solutions may simply lean on problem-specific prior
human knowledge to a degree that may not be possible on less-familiar or esoteric tasks within
private RDB repositories. Of course this is not meant to discourage LLM-based RDB frameworks,
and certainly TFMs equipped with gpf (e.g., RDBLearn, TabPFN-Rel-OSS, etc.) are a natural fit for
agentic enhancements, the topic of Section 7. We only advocate that some caution is warranted when
interpreting results, especially when extrapolating to new domains. While similar concerns have
certainly been raised with other data modalities, we would argue that the situation is more acute in
RDB regimes with only limited, relatively well-known benchmarking sources that are susceptible to
memorized solutions.

et al., 2024) andRelBench-v2(Gu et al., 2026). Note that RelBench-v1 datasets and tasks are also
equivalent to the recently-postedRelArena- α benchmarking platform (Hayler et al., 2026) patterned
after TabArena (Erickson et al., 2026). The primary difference is that RelArena- α enforces more
rigid/standardized submission protocols that some published work on RelBench-v1 may not satisfy.
That being said, RDBLearn and TabPFN-Rel-OSS already adhere to these guidelines, and it is only
to the advantage of other models with which we compare if they do not. This means our results in
Figure 1 are actually conservative in showcasing the abilities of TFM-based approaches to RDB
predictive modeling.
Beyond the above, we test over five4DBInfer(Wang et al., 2024) binary classification datasets that
have been used in several recent works (Huang et al., 2026; Hudovernik et al., 2026), as well as the
multi-class predictive tasks from theSALTrepository (Klein et al., 2024) as adopted by Hudovernik
et al. (2026). Standard train/dev/test splits are used for all experiments. Note that for RelBench-v1,
we omit only rel-f1 and rel-event datasets because of potential leakage issues mentioned in prior
work, and we do not have results for all baseline models on these datasets.

G DETAILS OFINTERACTIONEXPERIMENTS
This section describes the detailed setup for experimenting with the interaction terms discussed in
Sections 6 and 7, particularly as they relate to Figure 3.
G.1 SETUPBEHINDFIGURE3 (LEFT)
Data generation.Each synthetic RDB contains two tables, a target/parent T 1 and a child T 2. Table
T 1 contains two columns (PK and a label) and 4000 rows (3200 for training and 800 for testing).
Each row of T 1 is linked to l rows of T 2 via PK-FK pairs, where T 2 is composed of a single FK
column as well as two signal columns {a,b} mixed within a variable number of uninformative
columns. We set l∼Uniform{2, . . . ,20}. Signal columns are synthesized with Bernoulli(0.3) for
binary variants or N(0,1) for Gaussian ones, alongside d2 −2 additional columns drawn IID from
the same respective family, for total widthsd 2 ∈ {8,16,32,64,96}forT 2 instantiations.
Label synthesis.We incorporate 4 labeling functions to cover both linear and nonlinear relation-
ships. For each row in the task table where PK=i , let Ri ={j∈T 2 where FKj =i} . Labels are
generated by aggregating the row-level interaction with different the aggregation functions:
•mean:y i =mean j∈Ri ajbj ;
•thresholded count:y i =count j∈Ri (ajbj >1);
•parity:y i = L j∈Ri (aj ∧b j) ;
•prod agg:y i =mean Ri (a)·mean Ri (b).
We remark that prod agg is favorable to RDBLearn since gpf already computes this form of
interaction between aggregations, as mentioned in Section 6. Meanwhile, the other aggregation
choices are not favorable to RDBLearn since they are not computed by any single aggregation
(although combinations thereof may approximate them). For different labeling rules, we experimented
with different data column distributions as follows:
•parity,mean, andprod aggwith binary columns;
•count(ab >1)with Gaussian columns.
Together these selections give us the four tasks listed in Figure 3 (left).
Experiment models.We compare TFM-based RDBLearn against the top non-TFM-based RDB
FMs, KumoRFM-2 (Hudovernik et al., 2026) and RT-J (Ranjan et al., 2026b), all in-context with
no task-specific training or fine-tuning. RDBLearn simply uses H= 2 to match the KumoRFM-2
default setting, run from a local deployment of the published model. RT-J uses the public zero-shot
checkpoint for FM operational mode (i.e., no fine-tuning). For both KumoRFM-2 and RT-J we first
validated our implementation pipeline by reproducing performance numbers from the respective
published papers.
G.2 QUASI-REALWORLDRDB USED INFIGURE3 (RIGHT)
We adopt the rel-trial RDB (Robinson et al., 2024) for the quasi-real world interaction experiment. We
do not modify the actual schema; instead, for each trial we pick two numerical or categorical columns
{a,b} co-located in one child table of the task entity, and define each task label as the temporally-
valid mean of the row-level product ajbj over the linked child rows, computed strictly over rows
dated before the task timestamp. The same per-row cutoff column is consumed by all three models,
so no model can access post-cutoff rows during labeling or inference. Column pairs touching value
columns whose measurement unit varies across rows (param value and the confidence-interval
limits, whose unit depends on a sibling code column) are excludeda prioriand outcome-blind,
leaving nine child-table pairs. These pairs form the x-axis labels of Figure 3 (right).
We repeat the above experiment, this time explicitly adding an additional child-table column formed
from this so-called “golden feature” interaction term. This is meant to reflect a hypothetical scenario
27

whereby an informed agent has supplied this product term as an additional useful feature. We then
explore the degree to which each RDB FM can effectively utilize this column to improve predictive
performance in Figure 3 (right).
H DETAILS OFREAL-WORLDAGENTICEXPERIMENT
Following the pointer at the end of Section 7, this experiment represents a preliminary proof-of-
concept, not an exhaustive exploration of possibilities. And certainly there are more principled ways
of incorporating agents within a TFM-based paradigm than what we have done. We also stress one
additional point upfront: Even as agents are often able to generate useful predictive features, this
typically requires extensive domain knowledge and/or meta-data associated with a given RDB (this
may also introduce new pathways for leakage and/or memorization that could artificially inflate
performance; see Appendix D). In contrast, TFM-based models like RDBLearn and TabPFN-Rel
can in principle operate out of the box in new domains without such knowledge, providing greater
flexibility and privacy.
H.1 EXPERIMENT SETUP
TFM-based methods leverage agent-friendly SQL-based RDB harnesses, where SQL queries are
automatically generated to aggregate features from RDBs. These queries are agent-readable and
provide an alternative entry point for understanding the predictive modeling task and core RDB
structure. Based on this observation, we prompt Cursor Grok 4.5 under the default Cursor 3.6.31
harness. We provide a single prompt together with the raw training set and the corresponding features
generated by the RDBLearn encoder gpf. Note that we do not allow the agent to iterate (e.g., by using
a loop). Therefore, the feature generation is a single forward pass. This is substantially different
from the SOTA RelAgent (Huang et al., 2026), which trains numerous fully-supervised models (on a
per-task basis) across multiple iterations of a multi-agent system.
For our experiments, the prompt for all tasks is the same except for the task name. As a representative
example, the rel-trial prompt is as follows:
Prompt for Cursor Grok 4.5 to generate RDB features
If you look into what the rel-trial/study outcome tasks are, understand what the goal is, then
look into DFS-depth 4 (including hop 1-4) SQLs. Can you analyze what features are useless
and what new useful feature column you can add to the flattened table by SQL?”
H.2 LEAKAGECHECK
For our experiment, only the training set is exposed to the agent. To investigate whether there is data
leakage, we manually look into the trace and prompt the agent to self-check. As a result, two features
for rel-event tasks were found aggregating future (the same week) data. They aresql hist ignore rate
andsql hist repeat rate, which calculate past-week label statistics. Although the target predictive
entity is excluded from the calculation, when this predictive entity correlates with a mid-week date,
same-week future label information can still be included. (For reference, performance results in
Table 7 below exclude these two features.) Beyond this, inspecting every tool call in the agent trace,
we did not observe any behavior that would indicate retrieval/access of validation or testing set
information.

I.3 PROOF OFPROPOSITIONB.1
High-Level Intuition.To illustrate the gist of this result, assume that the ground-truth label ytest for
any xtest is given by a parity check on available labels in G∗ H (xtest). This labeling rule is impossible
to determine from yH (xtest) alone, since for any node x′ associated with a label y′ ∈y H (xtest), the
corresponding set yH (x′) need not be fully observed, i.e., the overlap between yH (x′) (with a known
label for x′) and yH (xtest) (with an unknown label for xtest) is only partial. Hence the parity rule is not
identifiable, as even a single missing label can flip the result. This disrupts inductive inference from
the information available within G∗ H (xtest), which is all a fixed FM encoder has access too. In contrast,
if per-dataset training is allowed over RDB instances formed via a given parity-based labeling rule,
it is straightforward to learn the associated mapping on a dataset-by-dataset or task-by-task basis.
We remark that, although the proof below relies on parity checks for illustrative convenience, the
underlying phenomena is emblematic of quite broad scenarios where diverse heterophilic (as opposed
to homophilic) relationships are dominant.
